### Risk Assessment

This story implements a connection pool with single-writer semantics - a critical concurrency component. Failures could result in:
- **Data corruption** from concurrent writes
- **Deadlocks** from improper semaphore handling
- **Resource leaks** from unreleased connections
- **Performance degradation** from pool starvation

**Note:** Retry mechanism risks are now addressed in STORY-1.3.1.

**Overall Risk Level:** HIGH - Concurrency primitives require thorough testing.

## Test Scenarios by Acceptance Criteria

### AC1: Semaphore for write operations (1 permit)

Single-writer enforcement is the most critical aspect of this pool.

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 1.3-UNIT-001 | Unit | P0 | Write semaphore initializes with exactly 1 permit | Pure state verification |
| 1.3-INT-001 | Integration | P0 | Second write connection blocks while first is held | Single-writer semantics validation |
| 1.3-INT-002 | Integration | P0 | Write connection released allows next writer | RAII permit release verification |
| 1.3-E2E-001 | E2E | P0 | Concurrent write requests serialize correctly under load | Real-world concurrency validation |

**Scenarios Detail:**

#### 1.3-UNIT-001: Write semaphore initialization
```
Given: A new DuckConnectionPool is created with any PoolConfig
When: The pool is instantiated
Then: The write_semaphore.available_permits() == 1
```

#### 1.3-INT-001: Single writer blocking (Story Test 1)
```rust
#[tokio::test]
async fn test_single_writer() {
    let pool = DuckConnectionPool::new(":memory:", PoolConfig::default()).await.unwrap();

    let write1 = pool.get_write_connection().await.unwrap();

    // Second write should block
    let write2_future = pool.get_write_connection();

    // Use timeout to verify it blocks
    let result = tokio::time::timeout(
        std::time::Duration::from_millis(100),
        write2_future
    ).await;

    assert!(result.is_err()); // Should timeout

    // Release first writer
    drop(write1);

    // Now second should succeed
    let write2 = pool.get_write_connection().await;
    assert!(write2.is_ok());
}
```

#### 1.3-INT-002: Writer release propagation
```
Given: A pool with blocked write request
When: Active write connection is dropped
Then: Blocked request acquires permit within 10ms
```

#### 1.3-E2E-001: Concurrent write serialization
```
Given: 100 concurrent write requests
When: Each writes a unique value to a shared table
Then: All writes succeed without corruption, final count = 100
```

**Scenarios Detail:**

#### 1.3-UNIT-002: Configurable read permits
```
Given: PoolConfig { max_readers: 5, ... }
When: Pool is created with this config
Then: read_semaphore.available_permits() == 5
```

#### 1.3-UNIT-003: Default configuration
```
Given: PoolConfig::default()
When: Config is inspected
Then: max_readers == 10
And: acquire_timeout_ms == 5000
```

#### 1.3-INT-003: Concurrent readers (Story Test 2)
```rust
#[tokio::test]
async fn test_multiple_readers() {
    let config = PoolConfig {
        max_readers: 5,
        ..Default::default()
    };
    let pool = DuckConnectionPool::new(":memory:", config).await.unwrap();

    // Should be able to get 5 readers concurrently
    let readers: Vec<_> = futures::future::join_all(
        (0..5).map(|_| pool.get_connection())
    ).await;

    assert!(readers.iter().all(|r| r.is_ok()));

    // 6th reader should timeout
    let result = tokio::time::timeout(
        std::time::Duration::from_millis(100),
        pool.get_connection()
    ).await;

    assert!(result.is_err());
}
```

#### 1.3-INT-004: Reader pool exhaustion
```
Given: Pool with max_readers: 5 and 5 active readers
When: 6th task calls get_connection() with short timeout
Then: 6th task receives ConnectionPoolTimeout error
```

async fn test_metrics() {

#### 1.3-INT-006: Timeout enforcement (Story Test 4)
```rust
#[tokio::test]
async fn test_timeout_returns_error() {
    let config = PoolConfig {
        max_readers: 1,
        acquire_timeout_ms: 50,
    };
    let pool = DuckConnectionPool::new(":memory:", config).await.unwrap();

    // Exhaust the single reader slot
    let _hold = pool.get_connection().await.unwrap();

    // Next request should timeout and return specific error
    let result = pool.get_connection().await;
    assert!(matches!(result, Err(Error::ConnectionPoolTimeout)));

    // Verify timeout metric incremented
    let metrics = pool.metrics();
    assert_eq!(metrics.timeouts, 1);
}
```

### AC5: Graceful shutdown support (`close()` method)

Critical for clean application termination.

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 1.3-INT-007 | Integration | P1 | close() waits for active connections before completing | Graceful shutdown |
| 1.3-INT-008 | Integration | P1 | New connection requests fail after close() initiated | Pool closed handling |
| 1.3-E2E-002 | E2E | P2 | Shutdown under load preserves data integrity | Real-world shutdown |

**Scenarios Detail:**

#### 1.3-INT-007: Close waits for completion (Story Test 6)
```rust
#[tokio::test]
async fn test_graceful_shutdown() {
    let pool = DuckConnectionPool::new(":memory:", PoolConfig::default()).await.unwrap();
    let conn = pool.get_connection().await.unwrap();

    // Start shutdown in background
    let pool_clone = pool.clone();
    let shutdown = tokio::spawn(async move {
        pool_clone.close().await
    });

    // Shutdown should wait for active connection
    tokio::time::sleep(Duration::from_millis(50)).await;
    assert!(!shutdown.is_finished());

    // Release connection
    drop(conn);

    // Now shutdown should complete
    shutdown.await.unwrap().unwrap();

    // New connections should fail with pool closed error
    assert!(matches!(pool.get_connection().await, Err(Error::ConnectionPoolClosed)));
}
```

#### 1.3-INT-008: Pool closed handling
```
Given: Pool with close() called
When: New task attempts get_connection() or get_write_connection()
Then: Returns Error::ConnectionPoolClosed immediately
And: Existing active connections continue functioning until dropped
```

#### 1.3-E2E-002: Shutdown under load
```
Given: Pool with 50 concurrent read operations in flight
And: 5 concurrent write operations in flight
When: pool.close() is called
Then: All in-flight operations complete successfully
And: close() returns after all complete
And: Database integrity verified (no partial writes)
```

## Additional Scenarios: RAII Cleanup Validation

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 1.3-INT-010 | Integration | P1 | Connection drop decrements active_readers/writers | RAII cleanup verification |
| 1.3-INT-011 | Integration | P1 | Connection drop releases semaphore permit immediately | Permit release timing |

**Scenarios Detail:**

#### 1.3-INT-010: Drop decrements metrics (Story Test 5)
```rust
#[tokio::test]
async fn test_raii_cleanup() {
    let config = PoolConfig {
        max_readers: 1,
        acquire_timeout_ms: 100,
    };
    let pool = DuckConnectionPool::new(":memory:", config).await.unwrap();

    {
        let _conn = pool.get_connection().await.unwrap();
        assert_eq!(pool.metrics().active_readers, 1);
    }

    // After drop, permit should be released
    assert_eq!(pool.metrics().active_readers, 0);

    // Should be able to acquire again immediately
    let _conn2 = pool.get_connection().await.unwrap();
    assert_eq!(pool.metrics().active_readers, 1);
}
```

#### 1.3-INT-011: Drop releases permit immediately
```
Given: Pool with max_readers: 1
And: 1 active reader (pool exhausted)
And: Task B waiting for read connection
When: Active reader dropped
Then: Task B acquires connection within 10ms
```
