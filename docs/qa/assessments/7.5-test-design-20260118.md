## Test Scenarios by Acceptance Criteria

### AC1: Enhanced Conformance JSON Schema

**Requirements:**
- Define JSON schema for enhanced conformance result
- Include all fields from `BmadConformanceResult`
- Maintain backward compatibility with existing agents

#### Scenarios

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 7.5-UNIT-001 | Unit | P0 | `MissingSection` serializes with `section_id`, `section_title`, `is_required` | Data integrity - all fields must be present |
| 7.5-UNIT-002 | Unit | P0 | `TypeViolation` serializes with `expected_type`, `actual_content`, `suggestion` | Data integrity - violation details critical for transformation |
| 7.5-UNIT-003 | Unit | P0 | `ChoiceViolation` serializes with `expected_choices` array and `actual_value` | Data integrity - enum validation feedback |
| 7.5-UNIT-004 | Unit | P1 | `ConformanceSuggestion` serializes `kind`, `description`, `auto_fixable` | Core feature - auto-fix detection |
| 7.5-UNIT-005 | Unit | P1 | Empty violations result in empty arrays, not null | Backward compatibility - prevent null pointer errors |
| 7.5-INT-001 | Integration | P1 | Round-trip: Rust struct → JSON → parse → verify all fields | Serialization contract validation |
| 7.5-INT-002 | Integration | P2 | Backward compatibility: new schema parseable by old agent using only basic fields | Non-breaking change verification |

---

### AC2: Handler Pipeline Integration

**Requirements:**
- Update `run_conformance_pipeline()` to pass full conformance data
- Serialize all violation structs
- Include `suggestions` with `auto_fixable` flags

#### Scenarios

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 7.5-INT-003 | Integration | P0 | Pipeline outputs full `BmadConformanceResult` for document with missing required section | Critical path - missing section is most common violation |
| 7.5-INT-004 | Integration | P0 | Pipeline outputs `TypeViolation` when section has wrong content type (e.g., paragraphs instead of checklist) | Critical path - type validation core to conformance |
| 7.5-INT-005 | Integration | P1 | Pipeline outputs `ChoiceViolation` when status field has invalid value | Core feature - enum validation |
| 7.5-INT-006 | Integration | P1 | Pipeline includes `suggestions` array with at least one `auto_fixable: true` for missing section | Feature validation - auto-fix enablement |
| 7.5-UNIT-006 | Unit | P1 | `ConformanceResultJson::from(BmadConformanceResult)` preserves all fields | Conversion correctness |
| 7.5-UNIT-007 | Unit | P2 | Large document (100+ sections) serializes without truncation | Edge case - scalability |

---

### AC3: TEA Agent Input Enhancement

**Requirements:**
- Update `document-conformance-agent.yaml` state schema
- Update `document-transformer-agent.yaml` to use enhanced data
- Add Lua helpers for accessing violation details

#### Scenarios

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 7.5-INT-007 | Integration | P1 | TEA conformance agent receives enhanced JSON with all violation types | Agent contract validation |
| 7.5-INT-008 | Integration | P1 | TEA transformer agent can access `missing_sections[0].is_required` from state | Lua access pattern validation |
| 7.5-E2E-001 | E2E | P1 | Full pipeline: non-conformant doc → TEA agent → agent outputs decision based on `is_required` | End-to-end feature validation |
| 7.5-E2E-002 | E2E | P2 | TEA agent logs warning when `type_violations` contains items | Observability validation |
| 7.5-UNIT-008 | Unit | P2 | Lua helper `get_required_missing()` filters `missing_sections` by `is_required=true` | Helper function correctness |

---

### AC4: CLI Reporting Command

**Requirements:**
- Add `agentfs graphdocs conformance-report <file>` command
- Output detailed conformance report in human-readable format
- Support `--json` flag for machine-readable output

#### Scenarios

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 7.5-E2E-003 | E2E | P1 | CLI command `conformance-report` outputs human-readable table with all violation types | User-facing feature validation |
| 7.5-E2E-004 | E2E | P1 | CLI command with `--json` flag outputs valid JSON matching schema | CI/automation support |
| 7.5-INT-009 | Integration | P2 | CLI command exits with code 1 when document is non-conformant | CI pipeline integration |
| 7.5-E2E-005 | E2E | P2 | CLI command handles missing file gracefully with helpful error | Error handling |
| 7.5-UNIT-009 | Unit | P2 | Human-readable formatter aligns columns correctly with long section names | Output formatting |
| 7.5-UNIT-010 | Unit | P2 | `--json` output is compact (no pretty-print) by default | Performance consideration |

## Risk Coverage

| Risk | Test IDs | Mitigation Strategy |
|------|----------|---------------------|
| Data loss during serialization | 7.5-UNIT-001, 002, 003, INT-001 | Comprehensive field verification |
| Backward compatibility breakage | 7.5-INT-002, UNIT-005 | Old agent parsing validation |
| TEA agent state access failure | 7.5-INT-007, 008, E2E-001 | Lua integration testing |
| CLI output corruption | 7.5-E2E-003, 004 | Format validation |

---

## Recommended Execution Order

1. **P0 Unit tests** (7.5-UNIT-001, 002, 003) - Fail fast on serialization issues
2. **P0 Integration tests** (7.5-INT-003, 004) - Validate pipeline integration
3. **P1 Unit tests** (7.5-UNIT-004, 005, 006) - Core functionality
4. **P1 Integration tests** (7.5-INT-005, 006, 007, 008) - Agent integration
5. **P1 E2E tests** (7.5-E2E-001, 003, 004) - User-facing validation
6. **P2 tests** as time permits
