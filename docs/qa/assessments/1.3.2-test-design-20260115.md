### Strategy Rationale

This story introduces a **connection pool** with **semaphore-based concurrency control** - a critical infrastructure component affecting all database operations. The test strategy emphasizes:

1. **Integration-heavy approach**: The core value proposition (parallel reads) can only be validated with real DuckDB connections, not mocks
2. **Performance benchmarks as tests**: Acceptance criteria explicitly require proving parallel > serial performance
3. **Concurrency correctness**: Race conditions and deadlocks are high-risk; extensive concurrent scenarios required
4. **Metrics accuracy**: Pool observability depends on correct counter updates

## Test Implementation Notes

### 1. Connection Behavior with `:memory:`
**Critical:** Each `Connection::open(":memory:")` creates a **separate database**. For shared access in tests, use `:memory:?cache=shared` or file-based paths.

```rust
// WRONG - each connection sees different data
let pool = DuckConnectionPool::new(":memory:")?;

// CORRECT for shared in-memory
let pool = DuckConnectionPool::new(":memory:?cache=shared")?;

// CORRECT for tests - use temp file
let pool = DuckConnectionPool::new("/tmp/test.duckdb")?;
```

### 2. Timing-Based Tests
Performance benchmarks should use conservative thresholds:
- Use 2x speedup threshold (not theoretical 8x) to account for system variance
- Run warmup iterations before measuring
- Consider CI environment constraints (shared resources)

### 3. Concurrent Test Safety
Tests involving concurrent operations must:
- Use `tokio::spawn` for independent tasks
- Use barriers or latches to synchronize start times
- Account for scheduling variability in assertions

### 4. Metrics Testing Under Concurrency
When testing atomic counters under load:
- Use `spawn_blocking` sleeps to ensure overlap
- Verify `active_*` counters at specific points using barriers
- Accept minor variance in `total_wait_time_ms` due to scheduling
