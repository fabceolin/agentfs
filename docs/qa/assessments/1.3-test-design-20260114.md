### Risk Assessment

This story implements a connection pool with single-writer semantics - a critical concurrency component. Failures could result in:
- **Data corruption** from concurrent writes
- **Deadlocks** from improper semaphore handling
- **Resource leaks** from unreleased connections
- **Performance degradation** from pool starvation

**Overall Risk Level:** HIGH - Concurrency primitives require thorough testing.

## Test Scenarios by Acceptance Criteria

### AC1: Semaphore for write operations (1 permit)

Single-writer enforcement is the most critical aspect of this pool.

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 1.3-UNIT-001 | Unit | P0 | Write semaphore initializes with exactly 1 permit | Pure state verification |
| 1.3-UNIT-002 | Unit | P0 | Write semaphore cannot be configured with >1 permits | Validation logic |
| 1.3-INT-001 | Integration | P0 | Second write connection blocks while first is held | Single-writer semantics validation |
| 1.3-INT-002 | Integration | P0 | Write connection released allows next writer | RAII permit release verification |
| 1.3-E2E-001 | E2E | P0 | Concurrent write requests serialize correctly under load | Real-world concurrency validation |

**Scenarios Detail:**

#### 1.3-UNIT-001: Write semaphore initialization
```
Given: A new DuckConnectionPool is created
When: The pool is instantiated with any PoolConfig
Then: The write_semaphore.available_permits() == 1
```

#### 1.3-UNIT-002: Write permit enforcement
```
Given: A PoolConfig with invalid write permits
When: Attempting to create pool with write_permits > 1
Then: Constructor rejects with InvalidConfiguration error
```

#### 1.3-INT-001: Single writer blocking
```
Given: A pool with one active write connection
When: A second task calls get_write_connection()
Then: Second task blocks until first connection is dropped
```

#### 1.3-INT-002: Writer release propagation
```
Given: A pool with blocked write request
When: Active write connection is dropped
Then: Blocked request acquires permit within 10ms
```

#### 1.3-E2E-001: Concurrent write serialization
```
Given: 100 concurrent write requests
When: Each writes a unique value to a shared table
Then: All writes succeed without corruption, final count = 100
```

### AC2: Pool of read connections (N permits)

Multiple concurrent readers are essential for read performance.

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 1.3-UNIT-003 | Unit | P1 | Read semaphore initializes with configurable permits | Configuration validation |
| 1.3-UNIT-004 | Unit | P1 | Default max_readers is 10 | Default configuration verification |
| 1.3-INT-003 | Integration | P1 | N concurrent readers succeed simultaneously | Parallel reader support |
| 1.3-INT-004 | Integration | P1 | N+1 reader blocks until one releases | Read pool exhaustion handling |
| 1.3-INT-005 | Integration | P2 | Readers and writers can coexist | DuckDB concurrent read/write support |

**Scenarios Detail:**

#### 1.3-UNIT-003: Configurable read permits
```
Given: PoolConfig { max_readers: 5, ... }
When: Pool is created with this config
Then: read_semaphore.available_permits() == 5
```

#### 1.3-UNIT-004: Default configuration
```
Given: PoolConfig::default()
When: Config is inspected
Then: max_readers == 10
```

#### 1.3-INT-003: Concurrent readers
```
Given: Pool with max_readers: 5
When: 5 tasks call get_connection() simultaneously
Then: All 5 acquire connections concurrently
And: metrics.active_readers == 5
```

#### 1.3-INT-004: Reader pool exhaustion
```
Given: Pool with max_readers: 5 and 5 active readers
When: 6th task calls get_connection()
Then: 6th task blocks
When: One reader is dropped
Then: 6th task acquires within timeout
```

#### 1.3-INT-005: Reader-writer coexistence
```
Given: Pool with 3 active readers
When: A write connection is requested
Then: Write succeeds (DuckDB allows concurrent read/write)
And: All readers continue functioning
```

### AC3: Pool usage metrics

Observability is critical for production monitoring.

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 1.3-UNIT-005 | Unit | P1 | PoolMetrics initializes all counters to zero | Initial state verification |
| 1.3-UNIT-006 | Unit | P2 | MetricsSnapshot is thread-safe (Relaxed ordering) | Atomic correctness |
| 1.3-INT-006 | Integration | P1 | Metrics accurately track connection lifecycle | Counter increment/decrement |
| 1.3-INT-007 | Integration | P2 | Metrics persist across connection churn | Long-running accuracy |

**Scenarios Detail:**

#### 1.3-UNIT-005: Metrics initialization
```
Given: A new PoolMetrics instance
When: Inspected before any operations
Then: All counters (reads_acquired, writes_acquired, timeouts, retries, active_readers, active_writers, total_wait_time_ms) == 0
```

#### 1.3-UNIT-006: Thread-safe snapshots
```
Given: Concurrent metric updates from multiple threads
When: snapshot() is called
Then: No data races (verify with ThreadSanitizer)
And: Values are consistent (monotonically increasing)
```

#### 1.3-INT-006: Lifecycle tracking
```
Given: Pool with no connections
When: 2 readers and 1 writer acquired
Then: reads_acquired == 2, writes_acquired == 1
And: active_readers == 2, active_writers == 1
When: All connections dropped
Then: active_readers == 0, active_writers == 0
And: reads_acquired/writes_acquired unchanged
```

#### 1.3-INT-007: Churn accuracy
```
Given: Pool under sustained load
When: 1000 read + 500 write cycles complete
Then: reads_acquired == 1000, writes_acquired == 500
And: active_readers == 0, active_writers == 0
```

### AC4: Configurable timeout

Prevents indefinite blocking in degraded conditions.

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 1.3-UNIT-007 | Unit | P1 | Default acquire_timeout_ms is 5000 | Configuration default |
| 1.3-INT-008 | Integration | P0 | Connection request times out after configured duration | Timeout enforcement |
| 1.3-E2E-002 | E2E | P2 | Timeout errors surface correctly to callers | Error propagation |

**Scenarios Detail:**

#### 1.3-UNIT-007: Default timeout
```
Given: PoolConfig::default()
When: Config is inspected
Then: acquire_timeout_ms == 5000
```

#### 1.3-INT-008: Timeout enforcement
```
Given: Pool with acquire_timeout_ms: 100
And: Write semaphore held by another task
When: get_write_connection() called
Then: Returns Error::ConnectionPoolTimeout after ~100ms
And: metrics.timeouts incremented
```

#### 1.3-E2E-002: Timeout error handling
```
Given: Application layer calling pool
When: Pool timeout occurs
Then: Error type is ConnectionPoolTimeout
And: Error can be retried at application level
```

### AC5: Automatic retry on busy

Improves resilience under transient contention.

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 1.3-UNIT-008 | Unit | P2 | Default retry_count is 3, retry_delay_ms is 100 | Configuration defaults |
| 1.3-INT-009 | Integration | P2 | Failed acquisition retries configured times | Retry logic |
| 1.3-E2E-003 | E2E | P1 | Retry success under intermittent contention | Real-world retry validation |

**Scenarios Detail:**

#### 1.3-UNIT-008: Default retry config
```
Given: PoolConfig::default()
When: Config is inspected
Then: retry_count == 3
And: retry_delay_ms == 100
```

#### 1.3-INT-009: Retry execution
```
Given: Pool with retry_count: 3, retry_delay_ms: 50
And: Write semaphore busy for first 2 attempts
When: get_write_connection() called
Then: Retries 2 times with ~50ms delay each
And: Succeeds on 3rd attempt
And: metrics.retries == 2
```

#### 1.3-E2E-003: Retry under contention
```
Given: Pool with 10 concurrent write requesters
And: retry_count: 5
When: All 10 request write connections
Then: All eventually succeed (no permanent failures)
And: Some retry metrics recorded
```

## Test Implementation Notes

### Test Infrastructure
- Use `tokio::test` for async tests
- Use `:memory:` for in-memory DuckDB instances
- Consider `tokio::time::pause()` for deterministic timeout tests
- Use `#[should_panic]` or error assertions for negative tests

### Mocking Strategy
- **Unit tests**: Mock DuckDB connection creation
- **Integration tests**: Use real DuckDB in-memory instances
- **E2E tests**: Full pool with actual concurrent tasks

### Recommended Test Crates
