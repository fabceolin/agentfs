## High Risk Requiring Attention

### DATA-001: Read Returns Stale .conformant When .source is Newer

**Score: 6 (High)**
**Probability**: Medium - Background conformance may be slow or fail
**Impact**: High - User reads outdated transformed content, not their latest save

**Analysis**:
The resolution priority is:
```
1. .conformant (if exists) → return with Jinja2 expansion
2. .source (if exists) → return with Jinja2 expansion
3. Physical file → return with Jinja2 expansion
4. ENOENT
```

Scenario:
1. User saves file at T1, .source updated
2. Background conformance starts
3. User reads file at T2 (conformance not complete)
4. .conformant exists from previous save (stale)
5. User reads stale .conformant, not their T1 content

**Mitigation**:
1. **Check mtime**: Compare .source mtime vs .conformant mtime
2. **Prefer fresher file**: If .source is newer, read from .source
3. **Stale detection**: Check for .conformant.stale.* files indicating in-progress update
4. **Document behavior**: Clear user docs about eventual consistency

**Proposed Resolution Logic**:
```rust
async fn resolve_content(&self, logical_path: &str) -> Result<String> {
    let conformant_path = format!("{}.conformant", logical_path);
    let source_path = format!("{}.source", logical_path);

    let conformant_mtime = self.fs.stat(&conformant_path).await?.map(|s| s.mtime);
    let source_mtime = self.fs.stat(&source_path).await?.map(|s| s.mtime);

    // Prefer conformant only if it's at least as fresh as source
    if let (Some(c_time), Some(s_time)) = (conformant_mtime, source_mtime) {
        if c_time >= s_time {
            return self.read_file(&conformant_path).await;
        } else {
            // Source is fresher, conformance may be in progress
            return self.read_file(&source_path).await;
        }
    }

    // ... rest of fallback logic
}
```

**Testing Focus**:
- Save file, read before conformance completes
- Verify user sees their latest content
- Test with slow conformance (injected delay)

## Medium Risks

### DATA-003: Variable Cache Becomes Stale

**Score: 4 (Medium)**
**Probability**: Medium - Long editing sessions, variables change
**Impact**: Medium - Outdated variable values in rendered content

**Analysis**:
```rust
struct ConformanceReadHandler {
    variable_cache: Mutex<HashMap<String, HashMap<String, String>>>,
}
```

The cache is populated per-read but not invalidated when database changes. For long-running FUSE mounts, cached variables may become stale.

**Mitigation**:
- Add TTL to cache entries (e.g., 60 seconds)
- Invalidate cache on write operations
- Clear cache on next read if file mtime changed
- Document cache behavior

### TECH-002: Hidden File Detection Misses Edge Cases

**Score: 4 (Medium)**
**Probability**: Medium - Various file naming patterns
**Impact**: Medium - Hidden files leak into readdir or visible files hidden

**Analysis**:
```rust
fn is_conformance_file(path: &str) -> bool {
    filename.ends_with(".source") ||
    filename.ends_with(".conformant") ||
    filename.contains(".conformant.failed") ||
    filename.contains(".conformant.stale.")
}
```

Edge cases:
1. `my-file.source.md` - incorrectly hidden (ends_with ".source")
2. `conformant.md` - correctly visible (doesn't match pattern)
3. `.conformant` (hidden file starting with dot) - edge case

**Mitigation**:
- Use more precise pattern: check for `.md.source`, `.md.conformant`
- Test with various filename patterns
- Document naming restrictions

### TECH-003: getattr Size Calculation Expensive

**Score: 4 (Medium)**
**Probability**: Medium - Every stat() triggers getattr
**Impact**: Medium - Latency on file listings

**Analysis**:
```rust
async fn getattr(&self, path: &str) -> HandlerResult<Stats> {
    // Get resolved content for accurate size
    let content = self.resolve_content(path).await?;
    let expanded = self.expand_jinja2(path, &content).await?;
    stats.size = expanded.len() as u64;
}
```

This reads the entire file and expands Jinja2 just to calculate size. For large files or many files, this adds latency.

**Mitigation**:
- Cache expanded content with size
- Only expand on first getattr, cache result
- Accept approximate size (file size without expansion)
- Add flag for expensive vs fast getattr

### OPS-001: File Size Mismatch (ls vs cat)

**Score: 4 (Medium)**
**Probability**: Medium - Users may check file sizes
**Impact**: Medium - Confusion about file size discrepancy

**Analysis**:
With Jinja2 expansion:
- `ls -l file.md` shows expanded size (e.g., 1500 bytes)
- `cat file.md | wc -c` shows 1500 bytes (matches)
- `stat file.md.source` shows 800 bytes (unexpanded)

This is actually correct behavior but may confuse users.

**Mitigation**:
- Document behavior in user guide
- Ensure getattr returns expanded size consistently
- Provide `.source` access for raw size
