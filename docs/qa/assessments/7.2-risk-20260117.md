## High Risks Requiring Attention

### DATA-001: File/DB Desync Due to Post-Write DB Failure

**Score: 6 (High)**
**Probability**: High - Database operations can fail (connection, disk, constraint)
**Impact**: Medium - User queries return stale/inconsistent data vs file content

**Analysis**:
The implementation explicitly prioritizes file write over database sync:
```rust
match result {
    Ok(transformed) => {
        // Write .conformant file first
        fs.write_file(&conformant_path, transformed.as_bytes()).await?;

        // Sync to database (may fail)
        if let Err(e) = sync_to_database(&pool, &logical_path, &transformed).await {
            tracing::error!("Failed to sync to database: {}", e);
            // File is written, that's what matters most
        }
    }
}
```

This means:
- File (.conformant) written successfully
- Database sync fails
- Queries return stale data until next successful sync

**Mitigation**:
1. **Retry logic**: Implement exponential backoff retry for transient failures
2. **Sync queue**: On failure, queue document for background re-sync
3. **Dirty flag**: Track documents needing re-sync
4. **Mount-time reconciliation**: Detect file mtime > db updated_at

**Testing Focus**:
- Inject database failures after file write
- Verify retry behavior
- Test recovery on next save
- Integration test with real story document

### DATA-002: Variable Extraction Misses Content from Heading Pairs

**Score: 6 (High)**
**Probability**: Medium - Document structure varies
**Impact**: High - Missing variables make queries incomplete

**Analysis**:
The heading+content extraction pattern has edge cases:
```rust
let mut current_heading: Option<&str> = None;
for section in &doc.sections {
    if section.section_type == SectionType::Heading {
        current_heading = Some(&section.content);
    } else if let Some(heading) = current_heading {
        let var_name = heading_to_var_name(heading);
        insert_variable_with_inference(&conn, &doc_id, &var_name, section.content.trim())?;
        current_heading = None;  // Reset after first content!
    }
}
```

Edge cases:
1. **Multiple paragraphs under heading**: Only first paragraph captured
2. **Nested headings**: Parent gets child heading as content
3. **Tables/code blocks**: May not be captured correctly

**Mitigation**:
- Accumulate all content until next same-or-higher level heading
- Skip headings as variable values
- Template-aware extraction using section types
- Clear documentation of extraction rules

**Testing Focus**:
- Multi-paragraph sections (using real story document)
- Nested heading structures
- Mixed content types
- Verify all expected variables extracted

## Medium Risks

### TECH-001: TEA Subprocess Failure Loses Transformation

**Score: 4 (Medium)**
**Probability**: Medium - Subprocess failures happen (OOM, signal, timeout)
**Impact**: Medium - Document remains as .source only

**Analysis**:
The implementation handles TEA failures gracefully:
```rust
if transformer.check_tea_available().await.unwrap_or(false) {
    match transformer.transform_to_template(...).await {
        Ok(content) => content,
        Err(e) => {
            tracing::warn!("TEA failed, using rule-based: {}", e);
            transformer.transform_rule_based(...)?
        }
    }
} else {
    transformer.transform_rule_based(...)?
}
```

With rule-based fallback, total failure is less likely. If both fail, `.conformant.failed` is created.

**Mitigation**:
- Rule-based fallback (implemented)
- `.conformant.failed` file with error details (implemented)
- Retry on next save
- Admin command for manual re-conformance

### TECH-003: Race - Source Modified During Transformation

**Score: 4 (Medium)**
**Probability**: Medium - Users may save rapidly
**Impact**: Medium - Stale conformant written

**Analysis**:
The implementation includes mtime-based race detection:
```rust
// Check if source was modified during processing
let current_mtime = fs.stat(&source_path).await?.map(|s| s.mtime);
if current_mtime != Some(source_mtime) {
    tracing::info!("Source modified during conformance, aborting");
    return Ok(()); // Don't write stale conformant
}
```

**Mitigation**: Already implemented. Consider content hash for coarse-grained filesystems.

### PERF-001: Database Sync Latency

**Score: 4 (Medium)**
**Probability**: Medium - Database operations take time
**Impact**: Medium - Delays between save and query visibility

**Note**: This is background latency, not blocking the user.

**Mitigation**:

### PERF-002: Journal Table Growth Unbounded

**Score: 4 (Medium)**
Every sync creates journal entries:
- 1 for document upsert
- N for sections (50-100 for large docs)
- M for variables (20-50)

**Mitigation**:
- Implement journal compaction
- Archive old entries
- Monitor journal size

---

### OPS-001: No Notification When Conformance Fails

**Score: 4 (Medium)**
**Probability**: Medium - Failures happen
**Impact**: Medium - User doesn't know conformance didn't run

**Analysis**:
With background conformance, users may not notice failures. The `.conformant.failed` file exists but is hidden from readdir.

**Mitigation**:
- Log warnings at info level
- Consider xattr or status endpoint
- Admin command to list failed conformances
- IDE integration to show status
