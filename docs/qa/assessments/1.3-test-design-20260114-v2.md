### Risk Assessment

This story implements a connection pool with single-writer semantics - a critical concurrency component. Failures could result in:
- **Data corruption** from concurrent writes
- **Deadlocks** from improper semaphore handling
- **Resource leaks** from unreleased connections
- **Performance degradation** from pool starvation
- **Availability issues** from missing retry/shutdown handling

**Overall Risk Level:** HIGH - Concurrency primitives require thorough testing.

## Test Scenarios by Acceptance Criteria

### AC1: Semaphore for write operations (1 permit)

Single-writer enforcement is the most critical aspect of this pool.

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 1.3-UNIT-001 | Unit | P0 | Write semaphore initializes with exactly 1 permit | Pure state verification |
| 1.3-UNIT-002 | Unit | P0 | Write semaphore cannot be configured with >1 permits | Validation logic |
| 1.3-INT-001 | Integration | P0 | Second write connection blocks while first is held | Single-writer semantics validation |
| 1.3-INT-002 | Integration | P0 | Write connection released allows next writer | RAII permit release verification |
| 1.3-E2E-001 | E2E | P0 | Concurrent write requests serialize correctly under load | Real-world concurrency validation |

**Scenarios Detail:**

#### 1.3-UNIT-001: Write semaphore initialization
```
Given: A new DuckConnectionPool is created
When: The pool is instantiated with any PoolConfig
Then: The write_semaphore.available_permits() == 1
```

#### 1.3-UNIT-002: Write permit enforcement
```
Given: A PoolConfig with invalid write permits
When: Attempting to create pool with write_permits > 1
Then: Constructor rejects with InvalidConfiguration error
```

#### 1.3-INT-001: Single writer blocking
```
Given: A pool with one active write connection
When: A second task calls get_write_connection()
Then: Second task blocks until first connection is dropped
```

#### 1.3-INT-002: Writer release propagation
```
Given: A pool with blocked write request
When: Active write connection is dropped
Then: Blocked request acquires permit within 10ms
```

#### 1.3-E2E-001: Concurrent write serialization
```
Given: 100 concurrent write requests
When: Each writes a unique value to a shared table
Then: All writes succeed without corruption, final count = 100
```

### AC5: Automatic retry on busy (CRITICAL - PREVIOUSLY UNTESTED)

Improves resilience under transient contention. **This section has been significantly expanded to address QA Gate concerns.**

| ID | Level | Priority | Test Description | Justification |
|----|-------|----------|------------------|---------------|
| 1.3-UNIT-008 | Unit | P2 | Default retry_count is 3, retry_delay_ms is 100 | Configuration defaults |
| 1.3-INT-009 | Integration | P0 | **[NEW - P0 upgraded]** Failed acquisition retries configured times before failing | Retry logic - core requirement |
| 1.3-INT-009a | Integration | P0 | **[NEW]** Retry succeeds when semaphore becomes available during retry window | Retry success path |
| 1.3-INT-009b | Integration | P1 | **[NEW]** Retry respects delay between attempts | Timing validation |
| 1.3-INT-009c | Integration | P1 | **[NEW]** metrics.retries incremented on each retry attempt | Retry observability |
| 1.3-E2E-003 | E2E | P1 | Retry success under intermittent contention | Real-world retry validation |

**Scenarios Detail:**

#### 1.3-UNIT-008: Default retry config
```
Given: PoolConfig::default()
When: Config is inspected
Then: retry_count == 3
And: retry_delay_ms == 100
```

#### 1.3-INT-009: Retry execution on exhaust [NEW - UPGRADED TO P0]
```
Given: Pool with retry_count: 3, retry_delay_ms: 10, acquire_timeout_ms: 5
And: Write semaphore held for duration of test
When: get_write_connection() called
Then: Attempts 1 initial + 3 retries (4 total attempts)
And: Returns Error::ConnectionPoolTimeout after all retries exhausted
And: metrics.retries == 3
And: Total elapsed time ~35ms (5ms timeout * 3 + 10ms delay * 3 - accounting for initial)
```

#### 1.3-INT-009a: Retry success on availability [NEW]
```
Given: Pool with retry_count: 3, retry_delay_ms: 50
And: Write semaphore held by task A
When: Task B calls get_write_connection()
And: Task A releases semaphore after 80ms (during retry window)
Then: Task B succeeds on 2nd or 3rd attempt
And: metrics.retries >= 1
And: metrics.writes_acquired == 2 (A + B)
```

#### 1.3-INT-009b: Retry delay timing [NEW]
```
Given: Pool with retry_count: 2, retry_delay_ms: 100
And: Write semaphore permanently held
When: get_write_connection() called
Then: Time between retry attempts is ~100ms (+/- 20ms tolerance)
And: Total elapsed time ~300ms (accounting for delays and timeouts)
```

#### 1.3-INT-009c: Retry metrics tracking [NEW]
```
Given: Pool with retry_count: 5
When: 3 concurrent writers contend for single permit
And: Each eventually succeeds after retries
Then: metrics.retries > 0
And: metrics.writes_acquired == 3
And: metrics.retries reflects total retry attempts across all writers
```

#### 1.3-E2E-003: Retry under contention
```
Given: Pool with 10 concurrent write requesters
And: retry_count: 5
When: All 10 request write connections
Then: All eventually succeed (no permanent failures)
And: metrics.retries > 0 (some retries occurred)
```

## Test Implementation Notes

### Test Infrastructure
- Use `tokio::test` for async tests
- Use `:memory:` for in-memory DuckDB instances
- Use `tokio::time::pause()` for deterministic timeout tests
- Use `#[should_panic]` or error assertions for negative tests
- **[NEW]** Use `tokio::time::advance()` for retry delay validation

### Mocking Strategy
- **Unit tests**: Mock DuckDB connection creation
- **Integration tests**: Use real DuckDB in-memory instances
- **E2E tests**: Full pool with actual concurrent tasks
- **[NEW]** For 1.3-INT-016: Use trait object or feature flag to inject connection creation failures

### Retry Testing Strategy [NEW]
```rust
// Example retry test setup
#[tokio::test]
async fn test_retry_success_when_available() {
    let pool = DuckConnectionPool::new(":memory:", PoolConfig {
        retry_count: 3,
        retry_delay_ms: 50,
        acquire_timeout_ms: 10,
        ..Default::default()
    }).await.unwrap();

    // Hold write semaphore
    let writer = pool.get_write_connection().await.unwrap();

    // Spawn task that will release after 80ms
    let release_task = tokio::spawn(async move {
        tokio::time::sleep(Duration::from_millis(80)).await;
        drop(writer);
    });

    // This should retry and succeed
    let result = pool.get_write_connection().await;
    assert!(result.is_ok());
    assert!(pool.metrics().retries >= 1);
}
```
