# Test Design: Story 4.3 - DuckDB FUSE Mount with GraphDocs

Date: 2026-01-17
Designer: Quinn (Test Architect)

## Test Strategy Overview

- Total test scenarios: 24
- Unit tests: 6 (25%)
- Integration tests: 14 (58%)
- E2E tests: 4 (17%)
- Priority distribution: P0: 6, P1: 12, P2: 6

## Risk Assessment Summary

| Risk | Probability | Impact | Priority |
|------|-------------|--------|----------|
| DuckDB migration breaks existing mounts | Medium | High | P0 |
| GraphDocsHandler not registered correctly | Medium | Medium | P1 |
| Virtual directory not visible in root listing | Low | Medium | P1 |
| Document rendering timeout/failure | Low | Medium | P1 |
| SQLite code paths left behind causing confusion | Low | Low | P2 |

## Test Scenarios by Acceptance Criteria

### AC1: Mount command uses DuckDB/DuckAgentFS exclusively (remove SQLite/AgentFS support)

**Requirement:** Mount command must open DuckDB databases exclusively, removing all SQLite support.

#### Scenarios

| ID | Level | Priority | Test | Justification |
|----|-------|----------|------|---------------|
| 4.3-UNIT-001 | Unit | P0 | DuckConnectionPool::new() opens DuckDB file successfully | Core functionality - pure pool initialization |
| 4.3-UNIT-002 | Unit | P1 | DuckConnectionPool::new() fails with clear error for invalid path | Error handling for bad paths |
| 4.3-INT-001 | Integration | P0 | Mount command opens valid .duckdb file and creates filesystem | Critical path - mount must work |
| 4.3-INT-002 | Integration | P0 | Mount command rejects SQLite .db files with appropriate error | Breaking change - must fail gracefully |
| 4.3-INT-003 | Integration | P1 | Mount command fails with clear error for non-existent database | Error handling for missing files |
| 4.3-E2E-001 | E2E | P0 | `agentfs mount demo.duckdb /mnt` successfully mounts filesystem | End-to-end user journey validation |

### AC2: GraphDocsHandler is registered when DuckDB database contains GraphDocs tables

**Requirement:** When `gd_documents` table exists, register GraphDocsHandler with the handler registry.

#### Scenarios

| ID | Level | Priority | Test | Justification |
|----|-------|----------|------|---------------|
| 4.3-UNIT-003 | Unit | P1 | Check for gd_documents table existence query returns correct boolean | Pure SQL result interpretation |
| 4.3-INT-004 | Integration | P1 | GraphDocsHandler registered when gd_documents table exists | Multi-component integration |
| 4.3-INT-005 | Integration | P1 | GraphDocsHandler NOT registered when gd_documents table absent | Conditional registration logic |
| 4.3-INT-006 | Integration | P2 | Handler priority correctly set (50) to handle before default | Priority ordering verification |

### AC3: GraphDocsDirInjector injects `/.graphdocs/` into root directory listings

**Requirement:** Root directory listings (`ls /`) must include `.graphdocs` virtual directory.

#### Scenarios

| ID | Level | Priority | Test | Justification |
|----|-------|----------|------|---------------|
| 4.3-INT-007 | Integration | P1 | readdir("/") includes ".graphdocs" entry | Directory injection verification |
| 4.3-INT-008 | Integration | P1 | readdir_plus("/") includes ".graphdocs" with correct stats | Stats injection verification |
| 4.3-INT-009 | Integration | P2 | .graphdocs not duplicated if somehow already present | Edge case - idempotency |
| 4.3-E2E-002 | E2E | P1 | `ls /mountpoint` shows .graphdocs directory | User-facing verification |

### AC4: `ls /.graphdocs/` lists all documents from `gd_documents` table

**Requirement:** Listing the virtual directory must show all documents with `.gd.md` extension.

#### Scenarios

| ID | Level | Priority | Test | Justification |
|----|-------|----------|------|---------------|
| 4.3-INT-010 | Integration | P1 | readdir("/.graphdocs") returns all documents from gd_documents | Database query to listing |
| 4.3-INT-011 | Integration | P1 | Document filenames have .gd.md extension (e.g., "readme.gd.md") | Filename format verification |
| 4.3-INT-012 | Integration | P2 | Empty gd_documents returns only "." and ".." entries | Empty state handling |
| 4.3-E2E-003 | E2E | P1 | `ls /.graphdocs/` shows expected document files | User-facing verification |

### AC5: `cat /.graphdocs/{doc_id}.gd.md` renders document via GraphDocsEngine

**Requirement:** Reading a document file must render it through the GraphDocsEngine with variable substitution.

#### Scenarios

| ID | Level | Priority | Test | Justification |
|----|-------|----------|------|---------------|
| 4.3-UNIT-004 | Unit | P1 | GraphDocsHandler::extract_doc_id extracts ID from path correctly | Pure path parsing logic |
| 4.3-UNIT-005 | Unit | P2 | extract_doc_id handles edge cases (nested paths, special chars) | Edge case path handling |
| 4.3-INT-013 | Integration | P0 | read("/.graphdocs/readme.gd.md") returns rendered markdown | Critical rendering path |
| 4.3-INT-014 | Integration | P1 | getattr("/.graphdocs/readme.gd.md") returns size of rendered content | File size accuracy |
| 4.3-INT-015 | Integration | P1 | Non-existent document returns ENOENT | Error handling |
| 4.3-E2E-004 | E2E | P0 | `cat /.graphdocs/readme.gd.md` outputs rendered document | User-facing critical path |

### AC6: Remove unused SQLite imports and AgentFSOptions from mount.rs

**Requirement:** Clean up SQLite-related code from mount.rs to prevent confusion and reduce technical debt.

#### Scenarios

| ID | Level | Priority | Test | Justification |
|----|-------|----------|------|---------------|
| 4.3-UNIT-006 | Unit | P2 | mount.rs does not import agentfs_sdk::AgentFSOptions | Code cleanup verification |
| 4.3-INT-016 | Integration | P2 | mount.rs does not call open_agentfs() | SQLite path removed |

2. **P0 Integration tests** (critical paths)

   - 4.3-INT-002: Reject SQLite files
   - 4.3-INT-013: Document rendering

   - 4.3-E2E-001: CLI mount command
   - 4.3-E2E-004: cat document

   - All P1 tests in order

5. **P2 tests** (as time permits)
   - All P2 tests

# Addendum: Manual Testing for TEA Conformance via FUSE Mount

> **Added**: 2026-01-17
> **Focus**: Non-conformant to conformant markdown conversion with TEA agent and Opik observability

## A. Prerequisites for TEA/Opik Testing

### A.1 Environment Requirements

| Component | Requirement |
|-----------|-------------|
| TEA | TEA binary installed with `llm-local` feature |
| Model | GGUF model at `~/.cache/tea/models/` |
| Opik | Opik server running (local or cloud) |
| Config | TEA configured with Opik observability enabled |

### A.2 TEA Installation Check

```bash
# Verify TEA is installed
tea --version

# Verify model exists
ls ~/.cache/tea/models/*.gguf
```

### A.3 Opik Configuration

Ensure TEA is configured to send traces to Opik in `~/.tea/config.yaml`:

```yaml
observability:
  enabled: true
  provider: opik
  endpoint: https://opik.example.com  # or http://localhost:5000
  api_key: ${OPIK_API_KEY}
```

## B. Manual Test Scenarios for TEA Conformance

### B.1 Scenario: Write Non-Conformant Markdown via FUSE

**Given-When-Then:**

```gherkin
Given a mounted AgentFS filesystem
When I write a non-conformant markdown file to the mount
Then the file should be stored in the filesystem
And I can later transform it to conformant format using TEA
```

**Manual Steps:**

```bash
# Step 1: Mount the database
mkdir -p /tmp/agentfs-mount
./target/release/agentfs mount cli/demo/demo.duckdb /tmp/agentfs-mount --foreground &

# Step 2: Create non-conformant markdown (missing required sections)
cat > /tmp/agentfs-mount/story-test.md << 'EOF'
# My Test Story

This is a simple story without proper structure.
It lacks the required Status, Description, and Tasks sections.

## Notes
Some random notes here.
EOF

# Step 3: Verify file was written
cat /tmp/agentfs-mount/story-test.md

# Step 4: Confirm it exists
ls -la /tmp/agentfs-mount/story-test.md
```

### B.2 Scenario: TEA Agent Conformance Transformation

**Given-When-Then:**

```gherkin
Given non-conformant markdown files in a directory with a BMAD template
When I run the graphdocs conform command
Then TEA agent should be invoked to transform the files
And conformance results should be displayed
And traces should be sent to Opik
```

**Manual Steps:**

```bash
# Step 1: Create test directory with template
mkdir -p /tmp/conformance-test
cat > /tmp/conformance-test/story-tmpl.yaml << 'EOF'
template:
  id: story-template
  name: Story Template
  version: "1.0"
  output:
    format: markdown
    filename: "story.md"

sections:
  - id: status
    title: Status
    type: choice
    choices: [Draft, InProgress, Review, Done]
    required: true

  - id: description
    title: Description
    type: paragraphs
    required: true

  - id: tasks
    title: Tasks
    type: checklist
    required: true

  - id: notes
    title: Notes
    type: paragraphs
    required: false
EOF

# Step 2: Create non-conformant document
cat > /tmp/conformance-test/story-1.md << 'EOF'
# Feature: User Authentication

## Notes
Need to implement login flow.
User should be able to reset password.

## Random Section
This section shouldn't exist in template.
EOF

# Step 3: Run dry-run conformance check
./target/release/agentfs graphdocs cli/demo/demo.duckdb conform /tmp/conformance-test --dry-run

# Expected output:
# Scanning directory: /tmp/conformance-test
# (dry-run mode - no files will be modified)
# [DRY-RUN] Would transform: /tmp/conformance-test/story-1.md (3 issues)
# --- Preview ---
# ... transformed content ...

# Step 4: Run actual conformance transformation
./target/release/agentfs graphdocs cli/demo/demo.duckdb conform /tmp/conformance-test

# Step 5: Verify transformed content
cat /tmp/conformance-test/story-1.md

# Expected: Document now has Status, Description, Tasks sections
```

### B.4 Scenario: End-to-End via FUSE Mount

**Given-When-Then:**

```gherkin
Given a mounted AgentFS with GraphDocs support
When I:
  1. Write a non-conformant markdown file
  2. Prepare a template for conformance
  3. Run TEA conformance transformation
  4. Import the transformed document to GraphDocs
  5. Read the document via /.graphdocs/
Then the rendered document should be conformant
And Opik should show the transformation trace
```

**Manual Steps:**

```bash
# === Setup ===
# Terminal 1: Mount database
mkdir -p /tmp/e2e-mount
./target/release/agentfs mount cli/demo/demo.duckdb /tmp/e2e-mount --foreground

# === Terminal 2: Execute test ===

# Step 1: Write non-conformant file
cat > /tmp/e2e-mount/my-feature.md << 'EOF'
# Add Dark Mode

Need to add dark mode to the app.
Users have been requesting this for months.

## Implementation Ideas
- Use CSS variables
- Detect system preference
- Add toggle in settings
EOF

# Step 2: Prepare template for conformance (separate directory)
mkdir -p /tmp/e2e-conform
cp /tmp/e2e-mount/my-feature.md /tmp/e2e-conform/
cat > /tmp/e2e-conform/story-tmpl.yaml << 'EOF'
template:
  id: feature-story
  name: Feature Story
  version: "1.0"
  output:
    format: markdown
    filename: "feature.md"

sections:
  - id: status
    title: Status
    type: choice
    choices: [Draft, InProgress, Review, Done]
    required: true
  - id: description
    title: Description
    type: paragraphs
    required: true
  - id: acceptance
    title: Acceptance Criteria
    type: checklist
    required: true
EOF

# Step 3: Run conformance transformation (invokes TEA)
./target/release/agentfs graphdocs cli/demo/demo.duckdb conform /tmp/e2e-conform

# Step 4: Import transformed document to GraphDocs
./target/release/agentfs graphdocs cli/demo/demo.duckdb import /tmp/e2e-conform/my-feature.md --id my-feature

# Step 5: Verify via .graphdocs virtual directory
cat /tmp/e2e-mount/.graphdocs/my-feature.gd.md

# Step 6: Check Opik dashboard for traces
echo "Check Opik dashboard for traces from document-transformer-agent"

# Step 7: Cleanup
fusermount -u /tmp/e2e-mount
```
