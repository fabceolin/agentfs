### Core Functionality

Semantic search API enables finding files by meaning rather than exact keywords:
- `search(query, options)` method for file-level semantic search
- `search_chunks(query, options)` method for chunk-level precision search
- CLI command `agentfs search` for user-facing search interface
- Result filtering by directory, extension, date range, and minimum score
- SearchResult struct with path, score, preview, stats, and optional chunk info

## Key Design Decisions

1. **Heavy Integration Focus (59%)**: Search operations involve database queries, embedding lookups, and complex filtering - integration tests against real DuckDB are the appropriate level for validating these behaviors.

2. **P0 for Semantic Relevance (2.3-E2E-007)**: The core value of semantic search is finding files by meaning. If "meeting notes about project" doesn't find project-related files, the feature fails its purpose. This is a critical user journey test.

3. **Filter Tests as P0/P1 Split**: Directory and extension filters are core functionality (P0) since they're the most commonly used. Date range filters are P1 as they're less frequently used but still important.

4. **Chunk Search Tests**: Chunk-level search enables more precise results for large files. Tests validate both the data structure (ChunkInfo) and the user experience (CLI display).

5. **CLI Testing Strategy**: E2E tests for CLI focus on user-visible behavior. Integration tests handle arg parsing internals. This split avoids slow E2E tests for logic that can be tested faster.

6. **Security Consideration (2.3-INT-022)**: SQL injection is a real risk since user queries are incorporated into database queries. Marked P2 because the implementation uses parameterized queries, but still needs validation.

7. **Status-Aware Testing**: Since AC1 is marked [DONE] but AC2-AC5 are pending, the test design acknowledges this. Implementation teams should prioritize tests for implemented functionality first.

### Assertion Patterns for Similarity

```rust
// Don't assert exact scores (embedding models vary)
// Instead, assert relative ordering
assert!(results[0].score > results[1].score,
    "Project-related file should rank higher than grocery list");

// For score bounds
assert!(results[0].score >= 0.0 && results[0].score <= 1.0,
    "Score must be normalized to [0, 1]");
```
