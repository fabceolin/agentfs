## High Risk Requiring Attention

### CONFIG-001: Overlay Path Resolution (Relative vs Absolute)

**Score: 6 (High)**
**Probability**: Medium - Users commonly use relative paths from working directory
**Impact**: High - Mount fails or wrong overlay loaded silently

**Analysis**:
The story shows validation:
```rust
if let Some(ref overlay_path) = args.overlay {
    if !overlay_path.exists() {
        return Err(anyhow::anyhow!(
            "Overlay file not found: {}",
            overlay_path.display()
        ));
    }
}
```

Edge cases:
1. **Relative path from shell**: `agentfs mount db /mnt --overlay agents/overlay/claude.yaml`
   - Resolved relative to CWD, which may not be project root

2. **Tilde expansion**: `--overlay ~/agents/overlay/claude.yaml`
   - Shell expands `~`, but what if quoted or escaped?

3. **Symlinks**: `--overlay /etc/agentfs/overlay.yaml` → symlink to actual file
   - `exists()` should follow symlinks, but worth verifying

4. **Daemonized mount**: When using `--foreground false`, CWD may change
   - Relative paths resolved before daemonize, but should use absolute internally

**Mitigation**:
1. **Canonicalize early**: Convert to absolute path immediately after validation
2. **Store absolute path**: In ConformanceConfig, always store canonicalized path
3. **Log resolved path**: Show user the actual path being used
4. **Document path handling**: State that relative paths are relative to CWD

**Testing Focus**:
- Mount with relative path from project root
- Mount with relative path from different directory
- Mount with absolute path
- Mount in daemon mode with relative path
- Verify logs show resolved absolute path

## Medium Risks

### CONFIG-002: Overlay File Syntax Invalid Causes Confusing TEA Error

**Score: 4 (Medium)**
**Probability**: Medium - YAML syntax errors are common
**Impact**: Medium - Confusing error message, user doesn't know what's wrong

**Analysis**:
The story validates that overlay file *exists*, but not that it's *valid YAML* or has *correct structure*. Invalid overlay is only discovered when TEA subprocess runs (during flush):

```
Error: TEA agent failed: invalid configuration: expected 'llm.provider' at line 3
```

User sees this error during file save, not during mount.

**Mitigation**:
1. **Validate at mount time**: Parse YAML and check required fields
2. **Pre-flight TEA check**: Run `tea --validate` or similar with overlay
3. **Clear error context**: "Overlay validation failed during mount"
4. **Accept MVP limitation**: Document that overlay validation happens at save time

**Testing Focus**:
- Mount with syntactically invalid YAML
- Mount with valid YAML but missing required fields
- Verify error messages are actionable

### CONFIG-003: agents_dir Default Doesn't Work in All Contexts

**Score: 4 (Medium)**
**Probability**: Medium - Default "agents" is relative path
**Impact**: Medium - Conformance silently falls back to rule-based

**Analysis**:
```rust
#[arg(long, value_name = "AGENTS_DIR", default_value = "agents")]
pub conformance_agents_dir: PathBuf,
```

Default "agents" is relative to CWD. If user mounts from `/var/run`:
1. `conformance_agents_dir = "agents"`
2. Resolved as `/var/run/agents`
3. TEA agents not found
4. Falls back to rule-based transformation
5. User expects Claude/GGUF but gets rule-based silently

**Mitigation**:
1. **No default**: Require explicit path for conformance
2. **Validate agents_dir**: Check it exists at mount time
3. **Log warning**: If agents_dir doesn't exist, warn user
4. **Document**: Default assumes CWD contains "agents" directory

**Testing Focus**:
- Mount from project root with default agents_dir
- Mount from different directory with default
- Mount with explicit agents_dir path
- Verify warning when agents_dir not found

### UX-001: User Confusion - Conformance Enabled by Default

**Score: 4 (Medium)**
**Probability**: Medium - Users may mount without understanding conformance
**Impact**: Medium - Unexpected file modification during save

**Analysis**:
With no options, conformance is **enabled** by default:
- User saves a markdown file in template-controlled directory
- File is transformed without explicit opt-in
- User surprised: "I didn't ask for transformation!"

This may be intentional design (conformance is a feature), but could surprise users.

**Mitigation**:
1. **Document default**: Make clear in help text that conformance is on
2. **Log on mount**: "Conformance checking enabled for template directories"
3. **First-transform notice**: Log when a file is first transformed
4. **Consider opt-in**: Require `--conformance` to enable (breaking change)

**Testing Focus**:
- Mount without options, verify conformance active
- Verify help text explains default behavior
- Manual test: save file, observe transformation

### TECH-001: ConformanceConfig Not Propagated Correctly

**Score: 3 (Low)**
**Probability**: Low - Standard Rust ownership/borrowing
**Impact**: High - Conformance silently broken

The config must flow: CLI args → MountArgs → ConformanceConfig → ConformanceWriteHandler.
Any break in this chain causes silent failure.

**Mitigation**: Integration test that verifies overlay is used.
