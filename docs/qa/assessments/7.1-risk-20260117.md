**Architecture Update (2026-01-18):** Story revised from blocking write to **non-blocking architecture**:
- Writes save to `.source` file immediately (no blocking)
- Background conformance task spawned after write
- Existing `.conformant` marked as `.conformant.stale.{timestamp}`
- User gets immediate write confirmation

## High Risks Requiring Attention

### TECH-001: Handler Priority Collision

**Score: 6 (High)**
**Probability**: Medium - Future handlers may want priority 20-30 range
**Impact**: High - Wrong handler intercepts writes, causing silent data corruption or missed conformance

**Analysis**:
The story assigns priority 25 to ConformanceWriteHandler, placing it between GraphDocsDirInjector (5) and GraphDocsHandler (50). Priority 20 is now used by ConformanceReadHandler (STORY-7.3).

Handler priority chain:
- 5: GraphDocsDirInjector
- 20: ConformanceReadHandler (NEW)
- 25: ConformanceWriteHandler (NEW)
- 50: GraphDocsHandler
- 100: DefaultHandler

**Mitigation**:
- Document the priority allocation scheme clearly
- Consider priority bands: 0-9 (critical), 10-29 (pre-processing), 30-69 (core handlers), 70-99 (post-processing), 100+ (fallback)
- Add handler priority validation in HandlerRegistry to warn on conflicts
- Unit test that verifies handler ordering

**Testing Focus**:
- Integration test with all handlers registered verifying correct dispatch order
- Test `can_handle()` returns false for non-conformance scenarios
- Test read handler runs before write handler for same path

---

### PERF-001: Background Task Queue Overwhelming System

**Score: 6 (High)**
**Probability**: Medium - Autosave features can trigger many saves per minute
**Impact**: High - System becomes unresponsive, memory exhausted from queued tasks

**Analysis**:
Every write triggers a background conformance task:
```rust
self.runtime.spawn(async move {
    if let Err(e) = run_background_conformance(...).await {
        tracing::error!("Background conformance failed: {}", e);
    }
});
```

Scenario:
1. User opens 10 files in editor with autosave
2. Autosave triggers every 30 seconds per file
3. Each save spawns a TEA subprocess (5-30s each)
4. Backlog of tasks grows, memory usage increases
5. System becomes sluggish

**Mitigation**:
1. **Debounce per file**: Wait 500ms after last write before spawning task
2. **Task deduplication**: Cancel previous pending task for same file
3. **Concurrency limit**: Max N concurrent conformance tasks
4. **Queue with backpressure**: Bounded channel for task queue
5. **Priority queue**: Recent writes before old ones

**Testing Focus**:
- Simulate 100 rapid writes to same file, verify only 1-2 conformance runs
- Test with 10 concurrent file edits, monitor memory/CPU
- Verify task cancellation works correctly

## Medium Risks

### TECH-002: Background Task Race Condition with Rapid Saves

**Score: 4 (Medium)**
**Probability**: Medium - Users may save rapidly during editing
**Impact**: Medium - Stale conformant from previous save overwrites newer content

**Analysis**:
The story includes mtime-based race detection:
```rust
// Before writing .conformant, verify source unchanged
let current_mtime = fs.stat(&source_path).await?.mtime;
if current_mtime != source_mtime {
    tracing::info!("Source modified during conformance, skipping write");
    return Ok(()); // Don't write stale conformant
}
```

This mitigates but doesn't eliminate all races:
1. Task A starts at mtime T1
2. User saves, Task B starts at mtime T2
3. Task A completes, checks mtime = T2 ≠ T1, aborts (correct)
4. Task B completes, writes .conformant (correct)

Edge case: If mtime granularity is coarse (some filesystems have 1-second resolution), two saves within same second may have same mtime.

**Mitigation**:
- Use content hash in addition to mtime
- Add sequence number to task tracking
- Log race detection for debugging

**Testing Focus**:
- Rapid save test: 10 saves in 1 second
- Verify final .conformant matches final .source
- Test on filesystem with coarse mtime

### DATA-001: .source File Orphaned

**Score: 4 (Medium)**
**Probability**: Medium - Background task failure (crash, OOM, timeout)
**Impact**: Medium - User reads outdated content, confusion

**Analysis**:
If background task never completes:
1. .source contains latest user content
2. .conformant (if exists) is stale
3. Read handler (STORY-7.3) falls back to .source (correct)
4. But user may not realize conformance didn't happen

**Mitigation**:
- Read handler prioritizes .source over stale .conformant (implemented)
- Log warnings for conformance failures
- Consider: retry queue for failed conformance
- Admin command to force re-conformance

---

### PERF-002: Template Detection I/O

**Score: 4 (Medium)**
**Probability**: Medium - FUSE operations call can_handle() frequently
**Impact**: Medium - Noticeable latency increase

**Mitigation**:
- Ensure `template_cache` is populated on mount
- Cache negative results (no template found)
- Add cache hit/miss metrics

---

### OPS-001: User Confusion About Versions

**Score: 4 (Medium)**
**Probability**: Medium - Users may wonder which version they're editing
**Impact**: Medium - Potential data loss if user doesn't understand model

**Analysis**:
With the non-blocking architecture:
- Writes go to .source
- Reads return .conformant (if available) or .source
- User editing sees the transformed version
- Next save transforms their edited version

This is the expected behavior but may confuse users.

**Mitigation**:
- Clear documentation of read/write flow
- `.source` suffix access for raw content
- Optional: Editor integration showing conformance status

## Low Risks

### TECH-004: Stale File Timestamp Collision

**Score: 2 (Low)**
Rapid saves within same second may create conflicting stale filenames.
**Mitigation**: Use millisecond or nanosecond timestamps.

### DATA-002: Stale File Accumulation

**Score: 2 (Low)**
If cleanup fails, stale files accumulate.
**Mitigation**: STORY-7.2 cleans up stale files on successful conformance; add periodic cleanup.

### OPS-002: Debugging Difficulty

**Score: 2 (Low)**
Multiple hidden files (.source, .conformant, .stale) complicate debugging.
**Mitigation**: Add RUST_LOG tracing; document file structure.

### OPS-003: Configuration Complexity

**Score: 2 (Low)**
Multiple config options (agents_dir, overlay, timeout).
**Mitigation**: Sensible defaults, validation on mount.
