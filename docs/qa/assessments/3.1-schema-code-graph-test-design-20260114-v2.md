### Core Functionality

Tables and views for code dependency graph analysis:
- `code_symbols` - Functions, classes, modules with metadata
- `code_dependencies` - Relationships between symbols (calls, imports, extends)
- Property Graph `code_graph` definition for DuckPGQ queries
- Indexes for efficient graph traversal
- FK relationship to `fs_current` for file association

### Use Cases Enabled

- **Impact Analysis**: What breaks if I change this function?
- **Dead Code Detection**: What code is never called?
- **Dependency Visualization**: How is the codebase connected?
- **Refactoring Support**: Safe rename, safe move operations

### TC-3.1-03: Dependency cascade on symbol deletion (maps to 3.1-INT-020)

```gherkin
GIVEN code_symbol 'test:a' exists
AND code_symbol 'test:b' exists
AND code_dependency 'test:a' -> 'test:b' exists
WHEN deleting code_symbol 'test:a'
THEN associated code_dependencies with source_id='test:a' are cascade deleted
AND code_symbol 'test:b' remains unaffected
```

**SQL Implementation:**
```sql
-- Setup
INSERT INTO fs_journal (inode, event_type, parent, name, mode)
VALUES (200, 'create', 1, 'test.rs', 33188);

INSERT INTO code_symbols (id, inode, name, kind)
VALUES ('test:a', 200, 'a', 'function'),
       ('test:b', 200, 'b', 'function');

INSERT INTO code_dependencies (source_id, target_id, dep_type)
VALUES ('test:a', 'test:b', 'calls');

-- Verify setup
SELECT COUNT(*) FROM code_dependencies WHERE source_id = 'test:a';
-- Expected: 1

-- Delete symbol
DELETE FROM code_symbols WHERE id = 'test:a';

-- Verify cascade
SELECT COUNT(*) FROM code_dependencies WHERE source_id = 'test:a';
-- Expected: 0 (cascaded)

SELECT COUNT(*) FROM code_symbols WHERE id = 'test:b';
-- Expected: 1 (unaffected)
```

### TC-3.1-04: Transitive dependency query with cycles (maps to 3.1-E2E-005)

```gherkin
GIVEN symbols A, B, C exist
AND dependencies A -> B, B -> C, C -> A exist (cycle)
WHEN querying transitive dependencies from A with depth limit 10
THEN query terminates within depth limit
AND returns A, B, C without infinite loop
AND execution time is < 1 second
```

**SQL Implementation:**
```sql
-- Setup cyclic graph
INSERT INTO fs_journal (inode, event_type, parent, name, mode)
VALUES (300, 'create', 1, 'cycle.rs', 33188);

INSERT INTO code_symbols (id, inode, name, kind)
VALUES ('cycle:a', 300, 'a', 'function'),
       ('cycle:b', 300, 'b', 'function'),
       ('cycle:c', 300, 'c', 'function');

INSERT INTO code_dependencies (source_id, target_id, dep_type)
VALUES ('cycle:a', 'cycle:b', 'calls'),
       ('cycle:b', 'cycle:c', 'calls'),
       ('cycle:c', 'cycle:a', 'calls');  -- Creates cycle

-- Transitive closure with depth limit
WITH RECURSIVE deps AS (
    -- Base case
    SELECT target_id, 1 as depth
    FROM code_dependencies
    WHERE source_id = 'cycle:a'

    UNION ALL

    -- Recursive case with depth limit
    SELECT d.target_id, deps.depth + 1
    FROM code_dependencies d
    JOIN deps ON d.source_id = deps.target_id
    WHERE deps.depth < 10
)
SELECT DISTINCT target_id, MIN(depth) as min_depth
FROM deps
GROUP BY target_id
ORDER BY min_depth;

-- Expected: Returns cycle:b (depth 1), cycle:c (depth 2), cycle:a (depth 3)
-- Query terminates due to depth limit, not infinite loop
```

### TC-3.1-05: Symbol ID uniqueness with overloaded methods (maps to 3.1-INT-019)

```gherkin
GIVEN class 'Calculator' has two methods named 'add'
AND method 1: add(int a, int b) -> int
AND method 2: add(float a, float b) -> float
WHEN inserting both with signature-hash-appended IDs
THEN both symbols coexist without collision
AND each can be queried independently
```

**SQL Implementation:**
```sql
-- Setup file
INSERT INTO fs_journal (inode, event_type, parent, name, mode)
VALUES (400, 'create', 1, 'calculator.rs', 33188);

-- Insert overloaded methods with signature hash in ID
INSERT INTO code_symbols (id, inode, name, kind, signature)
VALUES
    ('calc.rs:add#int_int', 400, 'add', 'method', 'fn add(a: i32, b: i32) -> i32'),
    ('calc.rs:add#float_float', 400, 'add', 'method', 'fn add(a: f64, b: f64) -> f64');

-- Verify both exist
SELECT COUNT(*) FROM code_symbols WHERE name = 'add';
-- Expected: 2

-- Verify can query each independently
SELECT signature FROM code_symbols WHERE id = 'calc.rs:add#int_int';
-- Expected: 'fn add(a: i32, b: i32) -> i32'

SELECT signature FROM code_symbols WHERE id = 'calc.rs:add#float_float';
-- Expected: 'fn add(a: f64, b: f64) -> f64'

-- Verify no PK collision
SELECT COUNT(DISTINCT id) FROM code_symbols WHERE name = 'add';
-- Expected: 2
```

## Key Design Decisions

1. **Heavy Integration Focus (56%)**: Code graph schema is database-centric with relational constraints. Unit tests validate enums and index presence; integration tests validate actual DuckDB behavior.

2. **P0 for FK Integrity**: The foreign key to `fs_current` is critical - invalid references would corrupt symbol-to-file mappings and break the entire code navigation use case.

3. **P0 for Graph Queries**: Impact analysis ("what breaks if I change this?") is the primary use case. If graph traversal fails, the entire feature fails.

4. **P0 for Circular Dependency Handling (NEW)**: Elevated from P1 to P0 because infinite loops could crash the system.

5. **E2E for DuckPGQ**: Property graph functionality depends on the DuckPGQ extension which may not be available in all environments. E2E tests isolate this optional dependency.

6. **Depth-Limited Recursion**: Transitive closure queries must handle circular dependencies. The recursive CTE depth limit (10 in spec) prevents infinite loops.

7. **Multi-Relationship Support**: The composite PK allows multiple relationship types between the same symbol pair (e.g., A calls B AND A imports B). This is validated explicitly.

8. **Overloaded Method Support (NEW)**: Added explicit test for signature-hash ID format to prevent collisions with overloaded methods, addressing risk identified in story QA notes.

## Appendix: DuckDB-Specific Considerations

### Foreign Key Enforcement

DuckDB enforces FK constraints by default. Test 3.1-INT-013 must verify the specific error message format:

```sql
-- DuckDB error format
-- Error: Constraint Error: Violates foreign key constraint because key "inode: 999" does not exist in the referenced table "fs_current"
```

### Index Verification

DuckDB uses `duckdb_indexes()` function for introspection:

```sql
SELECT index_name, table_name, is_unique
FROM duckdb_indexes()
WHERE table_name IN ('code_symbols', 'code_dependencies');
```

### Property Graph Extension

The DuckPGQ extension is experimental. Tests should use conditional logic:

```sql
-- Check if extension available before running property graph tests
SELECT installed, loaded FROM duckdb_extensions() WHERE extension_name = 'duckpgq';
```
