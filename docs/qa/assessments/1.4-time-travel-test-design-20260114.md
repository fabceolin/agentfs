### Core Functionality

Time-travel queries enable reconstructing filesystem state at any point in time by filtering events by `event_id`. Key capabilities:

1. **Snapshot API** - `snapshot_at(event_id)` returns read-only filesystem view
2. **Event Timeline** - `list_events(limit, offset)` provides paginated event history
3. **Diff API** - Compare two snapshots to identify changes
4. **CLI Commands** - `agentfs snapshot` for user interaction

### Critical Implementation Details

- Read-only `DuckAgentFSSnapshot` struct implements `FileSystem` trait
- Historical queries use CTE with `ROW_NUMBER() OVER (PARTITION BY inode ORDER BY event_id DESC)`
- Delete detection via subquery checking latest event_type per inode
- Diff builds change list from journal events between two event_ids

async fn test_snapshot_at_valid_event() {

#### 1.4-INT-019: Diff Detects Changes

```rust
#[tokio::test]
async fn test_diff_detects_changes() {
    let fs = DuckAgentFS::open(test_config()).await.unwrap();

    // Setup: Create file to be deleted
    fs.write_file("/deleted.txt", b"will be deleted").await.unwrap();
    let start = fs.current_event_id().await.unwrap();

    // Create changes
    fs.write_file("/new.txt", b"new file").await.unwrap();
    fs.write_file("/deleted.txt", b"modified").await.unwrap(); // Update first
    fs.remove("/deleted.txt").await.unwrap();

    let end = fs.current_event_id().await.unwrap();

    // Act
    let diffs = fs.diff(start, end).await.unwrap();

    // Assert - verify all change types detected
    assert!(diffs.iter().any(|d| matches!(d.change_type, ChangeType::Added)));
    assert!(diffs.iter().any(|d| matches!(d.change_type, ChangeType::Deleted)));
}
```

## Key Design Decisions

1. **P0 Focus on Read-Only Enforcement**: Snapshots must be immutable. Any bypass would corrupt audit trail integrity. All write methods tested at P0.

2. **Integration-Heavy (58%)**: Time-travel requires full database context. Unit tests insufficient for validating temporal query correctness.

3. **E2E for CLI**: User-facing commands require end-to-end validation to ensure correct argument parsing and output formatting.

4. **Explicit Edge Case Tests**: Event ID 0, renames, and moves are known complexity points. Dedicated tests prevent regression.

5. **Performance as P2**: Large journal handling is important but not blocking. Core correctness must pass first.

## QA Notes from Story Review

### Bug Found in Story Test Code

**Test 3 (test_diff) has a setup bug**: The test deletes `/deleted.txt` without creating it first. This will fail.

**Fix Required:**
```rust
// BEFORE (incorrect)
let start = fs.current_event_id().await.unwrap();
fs.remove("/deleted.txt").await.unwrap(); // File doesn't exist!

// AFTER (correct)
fs.write_file("/deleted.txt", b"will be deleted").await.unwrap();
let start = fs.current_event_id().await.unwrap();
fs.remove("/deleted.txt").await.unwrap();
```

### Security Concern

The `query_current()` method uses string formatting with `self.event_id`:
```rust
let historical_query = format!(
    "... WHERE event_id <= {} ...",
    self.event_id,  // Direct interpolation
);
```

While `event_id` is `i64` (not user-controlled string), this pattern should be flagged. Recommend parameterized query refactoring.

### Technical Debt

The historical CTE duplicates `self.event_id` three times:
1. `WHERE event_id <= {}`
2. `WHERE event_type = 'delete' AND event_id <= {}`
3. `WHERE j2.event_id <= {}`

Consider a single parameter binding or temporary table approach.
