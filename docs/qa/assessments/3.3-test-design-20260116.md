Designer: Quinn (Test Architect)

## Test Strategy Overview

- **Total test scenarios**: 24

## Risk Assessment

| Risk | Impact | Probability | Mitigation |
|------|--------|-------------|------------|
| Data corruption on historical queries | High | Medium | P0 integration tests for journal data integrity |
| Performance degradation with large journals | Medium | Medium | P1 performance tests with large event counts |
| SQL injection via event_id | High | Low | P0 input validation tests |
| Circular inheritance at point-in-time | High | Low | P1 inheritance chain tests |
| Journal entries not created on mutations | High | High | P0 journaling trigger/hook tests |

## Test Level Justifications

### Unit Tests (6 scenarios)

Appropriate for:
- Input validation logic (event_id, doc_id format)
- SQL query structure verification (static analysis)
- Data struct serialization/deserialization
- CLI argument parsing

**Not** testing at unit level:
- Actual database operations (requires integration)
- Time-travel query execution (requires journal data)

### Integration Tests (15 scenarios)

Primary test level because:
- Core functionality requires DuckDB interaction
- Journal creation is a database trigger/hook
- CTE queries need execution against real schema
- Connection pool behavior is exercised

Test environment:
- In-memory DuckDB with `schema/duckagentfs.sql` loaded
- Isolated test databases per test case
- Use `create_test_engine().await` helper pattern from STORY-3.1

### E2E Tests (3 scenarios)

Limited to critical CLI paths:
- Actual command execution validates full stack
- User-facing output format verification
- Integration between CLI and SDK

**Deferred to E2E**:
- File output (`--output` flag)
- History display formatting

## Implementation Notes for Dev Agent

### Test Helpers Needed

```rust
// Helpers to add to engine.rs tests module
async fn create_test_doc_with_journal(pool: &DuckConnectionPool, doc_id: &str, content: &str) -> i64;
async fn update_test_doc_with_journal(pool: &DuckConnectionPool, doc_id: &str, content: &str) -> i64;
async fn delete_test_doc_with_journal(pool: &DuckConnectionPool, doc_id: &str) -> i64;
```

### Schema Verification

Before running tests, ensure `schema/duckagentfs.sql` includes:
- `gd_journal` table with all columns
- `gd_event_seq` sequence
- Indexes on `(table_name, record_id)` and `(event_time)`

### Journal Population Strategy

Either:
1. **Trigger-based**: DuckDB triggers populate journal automatically (preferred if supported)
2. **Application-level**: Wrapper functions that INSERT to both main table and journal

Tests should verify whichever approach is implemented.
